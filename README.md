# ВышКат — учёт парка

Консольное приложение на Go для учёта парка кикшеринга «ВышКат»: приём транспорта через техосмотр,
вещи на балансе, отчёты по количеству и энергопотреблению, список транспорта для новичков и вывод
всех инвентарных номеров.

## Запуск

Нужен Go 1.22+. Зависимость `go.uber.org/dig` скачается автоматически при первом запуске.

```bash
go run .
```
Протестировать:
```bash
go test ./...
```

В меню пункт **6 — демо-сценарий**: он сам заполняет парк примерами и по очереди показывает все сценарии
(приём, три вида отказа техосмотра, вещи, отчёт, новички, инвентарные номера). Остальные пункты позволяют
сделать то же самое вручную.

## Структура

```
main.go                         сборка DI-контейнера (uber/dig) и запуск
domain/                         доменная модель
    inventory.go                интерфейсы Inventoried, EnergyConsumer, общая структура item
    vehicle.go                  интерфейс Vehicle, baseVehicle, реестр видов транспорта VehicleKind
    scooter.go                  Scooter (самокат)
    bicycle.go                  Bicycle (велосипед, без энергии)
    electric_bike.go            ElectricBike (электровелосипед)
    things.go                   Thing, Helmet, DockStation, ChargingCabinet
service/
    service_center.go           интерфейс ServiceCenter и реализация BasicServiceCenter
    park.go                     Park: приём транспорта и вещей, инвентарные номера
    park_report.go              отчёты Park: количество по видам, энергопотребление, новички
console/app.go                  консольное меню (только ввод/вывод)
```

## Логика решений

- **Две независимые абстракции.** `Inventoried` - всё, что стоит на балансе. `EnergyConsumer` - всё, что тратит энергию.
  Они не связаны: велосипед стоит на балансе, но энергию не тратит; док-станция - вещь, но энергию тратит. 
  `Park.TotalEnergy()` проходит по всем объектам на балансе и суммирует только те, что реализуют `EnergyConsumer`.
- **Реестр видов транспорта (Factory Method).** Каждый вид в `init()` регистрирует slug и фабрику
  (`VehicleFactory`). `HumanName` и `UsesEnergy` узнаёт у типа: название - из `Kind()`,
  расход - если тип реализует `EnergyConsumer`.
  `Slug` - служебный ключ для map, повторная регистрация вида с тем же slug завершается ошибкой.
- **Общие поля через встраивание.** Поля имени/номера лежат в `item`, простота - в `baseVehicle`.
  Конкретные типы их встраивают (в Go нет наследования, это композиция).
- **Инвентарный номер выдаёт парк** только после успешного техосмотра (`Park.AddVehicle`). Номера идут в одной общей 
  последовательности для транспорта и вещей
- **DI-контейнер** - библиотека [`go.uber.org/dig`](https://github.com/uber-go/dig). В `buildContainer()`
  (`main.go`) регистрируются конструкторы (`container.Provide`), а dig по типам их параметров сам
  понимает, что чему передать: `service.NewPark` принимает `ServiceCenter` → dig вызывает `newServiceCenter`.
  Каждая зависимость создаётся один раз. Запуск - `container.Invoke(func(app *console.App) {...})`.

## Обязательные вопросы

**Какой принцип SOLID применён наиболее явно и где?**  
DIP: `service.Park` принимает `ServiceCenter` (интерфейс, `service`) через
конструктор, а конкретную реализацию подставляет DI-контейнер в `main.go`. Также ISP -
разделение `Inventoried` и `EnergyConsumer` (`domain`).

**Какой принцип сознательно ограничен / «почти нарушен» и почему это приемлемо?**  
SRP в `service.Park`: он и хранит объекты, и выдаёт номера, и считает отчёты (`TotalEnergy`, `BeginnerVehicles`).
Получается почти божественный класс. Для удобства чтения отчёты вынесены в отдельный файл. 
Когда их кол-во вырастет, можно будет создать отдельный класс
Также OCP ограничен для вещей: вид вещи выбирается `switch` в `console/app.go`, без реестра как у
транспорта. 

**Что сломается (или не сломается) при расширении?**
- *Новый вид транспорта*  
  Не ломается: добавить файл `domain` с типом,
  методом `Kind()`, и `init()`, который вызывает `RegisterVehicleKind`.
  Название и потребление энергии реестр узнаёт у самого типа, консоль подхватит вид автоматически
- *Новый вид вещи*  
  Ломается: придётся менять `app.go`
- *Сотрудник*  
  Он не на балансе, поэтому не реализует `Inventoried` и не попадает в `Park`.
  Нужен отдельный пакет со своим хранилищем, существующий код не меняется, в консоли добавится пункт меню.
- *Склад запчастей*  
  Запчасть - это вещь на балансе, значит реализует `Thing`, и сразу появится в
  инвентарных номерах. Сам склад можно сделать отдельным сервисом и зарегистрировать в контейнере. 
  Ломаться ничего не будет; придётся добавить новые пункты в `addThing` консоли(сознательное ограничение OCP для вещей).

**Какой тест фиксирует решение техосмотра и/или правило «для новичков»?**  
Решение техосмотра проверяют TestInspect_AcceptsValidVehicle и TestInspect_RejectsInvalidVehicle.
Добавление в парк проверяют TestAddVehicle_AcceptedVehicleJoinsParkWithNextNumber и TestAddVehicle_RejectedVehicleReturnsReasonAndIsNotAdded.  
Правило «для новичков» проверяет TestBeginnerVehicles_SimplicityThreshold.

**Как подменяется зависимость?**. 
`Park` получает техосмотр через интерфейс `ServiceCenter` в конструкторе `NewPark`.
Реализацию подставляет DI-контейнер в `main.go`, а в тестах её передают вручную в виде заглушки stubServiceCenter.

```markdown
Проверить создание сервис-центра с лимитом расхода 3.0:
- создать ТС с корректными параметрами (непустое имя, простота от 1 до 10 и расход энергии 0 или 3.0) и проверить, что Inspect вернёт true

Проверить присвоение номеров и целостность последовательности:
- при последовательном добавлении элементов, номера для принятых элементов должны присваиваться последовательно без пропусков; элементы, отклонённые при проверке, не должны получать номер

Проверить подсчёт количества по видам в порядке появления:
```
